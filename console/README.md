# console/

Demo Console for the stage: a FastAPI back end and one HTML page, no build step.

**Presenter laptop only.** The console binds to `127.0.0.1` (a constant, there is no option to listen anywhere else) and rejects any request whose `Host` is not `127.0.0.1:<port>` or whose `Origin` is not `http://127.0.0.1:<port>`; state-changing requests must carry that `Origin`. It has no public endpoint of any kind and must never be exposed through a tunnel, a proxy or a port forward.

## Run

```
.venv/bin/python -m console            # http://127.0.0.1:8765/
.venv/bin/python -m console --port 8770
```

Run it from the repo root. It needs AWS credentials for the demo account in the environment (the same as the step scripts) and the packages in `requirements.txt`.

Sign in with a presenter account: `presenter1` or `presenter2` in the staff pool, group `presenter`. Their passwords are generated by the stack and stored in Secrets Manager as `<stack>/staff/presenter1` and `<stack>/staff/presenter2` (`gk-demo/...` for the default stack name); read one with the AWS CLI on the presenter laptop. The sign-in check uses the `approver` app client, whose tokens neither the Runtime nor the Gateway accepts, and drops the tokens after checking the group. The browser holds one opaque session cookie (HttpOnly, SameSite=Strict, 8 hours).

## What it shows

- Status strip, refreshed every 5 seconds: deputy mode, masking, notes guardrail, destination rule, prompt guard, approval rule, rate limit (SSM, `GetPolicy`, `GetGatewayRateLimit`).
- Left pane Maya Patel, right pane Leo Martinez. During M5b the right pane turns into Dana Kim's approval card: "Request approval" in Maya's pane appears after the approval rule denies a transfer; "Approve as Dana" signs Dana in with the `approver` client and records the approval in Maya's policy session through the Gateway.
- Decision feed, last 6 rows: time, persona, tool, decision, control, reason. Rows come from the agent stream, the Gateway trail (`TRAIL#<policy session ID>` rows in `gk-events`, polled every second during a turn) and the step scripts; rows for the same tool call merge.
- Moment tracker, a row under the status strip: one pill per stage in talk order (1 Front door, 2 Per-person tokens, 3 Act on behalf, 4 Masking, 5a Sequence rule, 5b Prompt guard, 5c Approval, 6 Rate limit; 5b is the internal M5c and 5c the internal M5b). Done stages are green with a check mark, the current one is orange, the rest grey. The server keeps the current stage (`/api/snapshot` field `moment`, `moment` events on the feed stream). It moves when a chip is sent (its step code), when a step script starts, when `goto.py` reaches its target and when `reset.py` finishes (no stage); click a pill to correct it (`POST /api/moment`). Below 1880 px wide, only the current pill keeps its name.
- Script banner, at the right end of the tracker when the row has no Run buttons: "Running: masking on" while a step script runs, then "Done: ..." (hides after 20 s) or "Failed: ..." (stays until the next banner). Step scripts post it through `scripts/steps/steplib.py` (the script channel, below).
- What changed: when a status read differs from the previous one, the changed item gets an orange outline and a CHANGED tag, until the next send in either pane, a New conversation, or 120 s.
- Per-step prompts in a picker; Enter sends, free typing works. A chip sends its step code with the prompt while the text box still holds the chip's prompt. "Connect partner account" opens the consent link from the agent's `consent` event; "Disconnect partner" revokes Maya's stored partner token (M2); "Direct call (M5)" makes the M5 transfer with no model, in Maya's policy session. "Direct call (M5b)" is the M5b fallback: after "Approve as Dana", it makes the $4,000 savings-to-checking transfer with no model, in Maya's current policy session, where the approval was recorded (start no new conversation in between).

The agent is driven through `scripts/agentlib.py` (the same client as the tests). Persona tokens stay in the console process and are never sent to the browser or logged; the request log is off.

## Step card and Run buttons

- Run buttons, at the right end of the tracker row: the steps whose card `show_in` is the current stage (before Moment 1, the steps with `show_in` `""`), in `order`, with `(clip NN)` when the step runs while a clip plays. Fallback steps sit behind one "Fallbacks" button that opens a small list. States: next (the first step without a successful run, blue outline), to do (grey), running (filled, with its seconds), done (green check), failed (red cross). While any step runs, every Run button is off. With Run buttons in the row, finished moments shrink to a check mark and their number and the script banner is hidden; if the row still does not fit (Moment 2), the moments still to come show their number only.
- Step card, in the feed's place: the kind badge (blue AgentCore or AWS API call, yellow demo switch, purple stand-in), the title, one sentence, the state with its seconds, Stop (for a run started by a Run button) and Close. Left: the real code from the card's excerpts, 26 px on a 1920 px screen, ligatures off, the key line in orange. Right: the command, then the live output (24 px, newest line at the bottom; the storm cards have a wider output pane). It closes with Close, or with a send in either pane once the step is no longer running (in Moment 6 the card stays during the storm). A new step replaces it; New conversation does not close it; `reset.py` clears it and every button's result.
- The cards are `console/cards/*.json` (schema: `console/cards/README.md`), loaded once at start by `console/stepcard.py`; an invalid card is skipped and named in `GET /api/steps` and in the pre-flight. A card change needs a console restart.
- `POST /api/steps/{id}/run` (presenter session and the Origin check): the id must be a loaded card (else 404); 409 while a step runs. The console starts `scripts/run_step.py <id> --run-id <its own id>` with its own interpreter from the repo root, in its own process group, stdin from /dev/null, output to `logs/run/step-<run id>.log` (the socket's directory), and kills the group after 300 s. Nothing from the request reaches the process. `POST /api/steps/stop`: SIGINT to that group, SIGTERM after 3 s, SIGKILL after 6 s. `POST /api/card/close` closes the card. `/api/snapshot` carries `card` and `step_runs`; the feed stream sends `card`, `card_lines` and `step_runs` events.
- `scripts/run_step.py <id>` (also run.sh entries 3 to 17; 7 is not used) prints `$ .venv/bin/python <argv...>`, runs the card's fixed command from the repo root, copies every line to the terminal and to the card (12-digit numbers masked), and exits with the step's code. A step started in the terminal shows on the card the same way, without Stop.

## Script channel

Step scripts, the runner, `goto.py`, `reset.py` and the pre-flight reach a running console through `console/client.py` (`post_row`, `post_moment`, `post_banner`, `post_card`, `health`) over a Unix socket, `logs/run/console.sock` (`GK_CONSOLE_SOCK` moves it for a test console, in both the console and the client). No token: the directory has mode 0700, the socket mode 0600, and the console closes any connection whose peer uid (`SO_PEERCRED`, Linux) is not its own. One JSON object per line, one reply per line, at most 64 KB; types `row`, `moment`, `banner`, `card_start`, `card_lines`, `card_end`, `card_clear`, `health`; every field is checked against an allowlist and a length, and no message can start a step. At start the console removes a stale socket file and refuses to start when another console answers on it; it removes its socket when it stops. A step script works the same when no console runs (each post is a quiet no-op). Over HTTP, only `POST /api/moment` remains of these, for the pill clicks (presenter session).

`health` over the socket: `started_utc`, `pid`, `port`, `status` (`state`, `error`, `read_at`), `moment`, `version` (the newest modification time of `console/*.py` and `console/static/index.html` when the console started), `cards` and `card_errors`. `scripts/preflight.py` check 7 uses it: the console runs, has working AWS credentials, runs the latest files, and loaded its cards with no errors. The page itself is read on every load, so a page change shows in a running console at once; a change to the Python files or the cards needs a console restart.
